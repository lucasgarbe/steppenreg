The Draw

Not a raffle — a lottery of entries. When registrations for a track exceed capacity, the draw decides who gets in. Here are the moving parts, verified against the current code.

33 draw tests passing 3 statuses: none / drawn / not_drawn 1 admin page that runs everything emails = manual step
01

The journey of one click

What actually happens between you pressing the button in the admin panel and the database being committed?

Safe to re-runThe pool only ever contains registrations without a draw status. Already-decided people are never re-drawn — running multiple rounds is officially supported.
The click commitsThere is no dry-run and no confirmation beyond your own double-check. The only undo afterwards is manually re-marking people in the Registrations table.
02

How the selection works

DrawService::selectRegistrations — individuals and teams all shuffle into one bag, then the bag is emptied slot by slot.

Always compare countsAfter drawing, check total_drawn in the success notification against the number you entered. A late big team can leave the last spots empty; only re-marking fixes that.
RandomnessThe shuffle is Laravel’s $pool->shuffle() (PHP’s standard RNG). Fine for an entry lottery; not cryptographically hardened, and the audit log records counts only — not the random order.
03

The life of a registration

Draw state lives in the draw_statuses table — one row per registration, all mutations flow through DrawService.

Teams move as oneMarking one team member (drawn or not) updates every member of that team, and they all share the same drawn_at. The lottery treats them the same way — atomic units.
Withdrawals aren’t automaticSomeone withdrawing after the draw frees a spot, but nobody is auto-promoted from the undrawn pool (open issue #19). Plan to do this by hand via row actions.
04

Hero list: what the draw does vs what you must do

The single most important distinction for tomorrow: the draw itself is fast and synchronous, the notifications are your job.

✓ Automatic (the moment you submit)

  • draw_statuses rows written for everyone in the pool
  • Domain events fired per affected registration
  • Starting numbers assigned to drawn participants
  • Audit trail + log entries written

→ Manual / queued (you drive this)

  • Registrations table → select rows → bulk action “Send Draw Result Emails”
  • Picks draw_success / draw_rejection per current status — mixed selection is safe
  • Needs a running queue worker; retries for 20h, failures logged
  • Post-draw withdrawal spot management (issue #19)
