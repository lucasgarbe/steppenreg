2. Selection algorithm DrawService::selectRegistrations

The question: who gets picked, and how do teams complicate the count?

flowchart TD A["Registrations for track,
no draw status yet"] --> B["Split into lottery units"] B --> B1["Individual = 1 unit

(size = member count)"] B1 --> C["Shuffle pool"] B2 --> C C --> D{"Walk pool in shuffled order"} D -->|"unit fits in remaining spots"| E["Select whole unit
spotsUsed += size"] D -->|"unit does NOT fit"| F["Skip unit entirely

Spot-waste quirk: if the remaining gap is smaller than a team's size, that team is skipped and the loop keeps going — the spots stay unused unless a later individual fits exactly. You may draw fewer participants than requested. Always compare total_drawn in the result notification against your input.
Randomness: the shuffle is Laravel's $pool->shuffle() (PHP's standard RNG). Good enough for a lottery; not cryptographically secure and not seed-reproducible. The audit log records counts, not the random order.

  • drawn Team members sync atomically: marking one member updates the whole team, and all members share the same drawn_at.
  • not_drawn drawn_at stays NULL — that is deliberate, not the bug described in issue #17.
  • no row Withdrawals after the draw do NOT auto-promote anyone from the undrawn pool — open issue #19. Handle manually via row actions.

Automatic after draw

draw_statuses rows, starting numbers, activity log entries, log lines.

Manual dispatch

Bulk action "Send Draw Result Emails" on selected rows (or per-row action). Job picks template by current status, so mixing drawn/not-drawn in one bulk send is safe.

Templates

draw_success, draw_rejection, plus a draw_waitlist template available if needed.
